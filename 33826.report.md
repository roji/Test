# Issue #33826 — Concurrent insert can cause AsSplitQuery to fail to populate unrelated child collections

**Issue:** https://github.com/dotnet/efcore/issues/33826

## Bug Status: **Confirmed** ✅

Reproduced on **both EF Core 8.0.24 and 10.0.3** on SQL Server. This is a long-standing bug, not a regression introduced in a specific version.

## Summary

When using `AsSplitQuery()`, if a concurrent insert adds a new parent entity (with children) between the execution of the first split query (parents) and the second split query (children), the materializer can silently drop **all** child entities for existing parents.

The root cause is in [`PopulateSplitIncludeCollectionAsync`](https://github.com/dotnet/efcore/blob/main/src/EFCore.Relational/Query/RelationalShapedQueryCompilingExpressionVisitor.ShaperProcessingExpressionVisitor.ClientMethods.cs#L566): when iterating through child query results, the code assumes rows are strictly ordered by parent identifier. The moment it encounters a child row whose parent identifier doesn't match the current parent, it **immediately stops** reading — even if matching rows exist later in the result set.

## Reproduction Mechanism

1. Seed `Blog(Id=10)` with two posts
2. Execute `Blogs.Include(b => b.Posts).AsSplitQuery().ToListAsync()`
3. Between the two split queries (detected via `LogTo`), insert `Blog(Id=1)` with a post — the lower ID is key
4. The child (posts) query returns rows ordered by `BlogId`: Blog 1's post first, then Blog 10's posts
5. The materializer processes Blog 10 (the only parent from query 1), reads the first child row (BlogId=1), sees it doesn't match, and **stops** — Blog 10 gets an empty `Posts` collection

**Expected:** `Blog 10: Posts=[Post1, Post2]`
**Actual:** `Blog 10: Posts=[]`

## Key Observations

- The bug manifests when the concurrently-inserted parent has a sort key that positions its children **before** existing children in the ORDER BY of the split query
- The correct data IS fetched from the database; EF just discards it during materialization
- The issue is independent of the #26808 fix ("more consistent ordering for split queries" in EF 10) — that fix addresses different ordering problems but doesn't help here
- While split queries are documented as not guaranteeing consistency without serializable/snapshot transactions, this behavior is unexpectedly severe: inserting an **unrelated** parent+children silently causes **all** children of **existing** parents to disappear
